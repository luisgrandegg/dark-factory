# Skill: migration-generation

The `migration-generation` skill scaffolds a single empty migration
file in the canonical location for the toolchain in use, and opens a
draft PR tagged `needs-human`. It does **not** write the migration
body and does **not** execute migrations.

This is the only factory skill that deliberately writes inside an
**approval-gate path** for some toolchains (`migrations/**` for
Alembic / Knex / raw-SQL). The safety story is therefore the
strictest in the repo.

The terse, operational version lives in
[`.claude/skills/migration-generation/SKILL.md`](../../.claude/skills/migration-generation/SKILL.md);
this is the long-form rationale.

## Why this shape

### Scaffold only — never the body

We could try to be clever: read the issue body, parse "add column
`email` to `users`," generate `op.add_column("users", sa.Column("email", sa.Text(), nullable=True))`.
We don't. Two reasons:

1. **Correctness liability.** A migration is one of the few changes
   in a codebase where a wrong line on production data can be
   irreversible. The factory does not have the operational
   awareness (current schema state, tenant data, transaction
   semantics) to write that body safely.
2. **Reviewer cognitive load.** A scaffold is a 10-line file with
   one TODO. A reviewer can verify it's structurally correct in
   seconds. A model-aware autogenerated migration would need
   line-by-line review of *what it ran against*, *whether the
   model edit was correct*, and *whether the generated migration
   matches reality*. That review is much harder than just writing
   the body in the first place.

So the skill produces:
- The right filename (timestamp / sequence per toolchain).
- The right location (per toolchain convention).
- The required boilerplate (class declarations, exports, etc.).
- A single `# TODO: human writes the migration body` comment
  inside the up/down / change block.

That's it. The human fills in the body in the PR before marking it
ready.

### Approval gate is the safety net, not the only one

`needs-human` is on `policy.approvalGates` (see `.factory/policy.yml`),
so the integrate sealer refuses to auto-merge the PR even if all CI
checks pass. The skill **always** applies that label, regardless of
which toolchain it targets — Django and Rails migrations don't live
under `migrations/**`, so the path-pattern gate wouldn't catch them.

This is intentional defence in depth: the skill could change tomorrow
to drop the label by mistake; the path gate would still catch
Alembic/Knex/raw-SQL migrations. Both gates need to fire for the
skill to be safe.

### No database connection

The skill does not run:

- `alembic upgrade head` / `alembic downgrade`
- `python manage.py migrate` / `... makemigrations --autogenerate`
- `bundle exec rails db:migrate` / `db:rollback`
- `knex migrate:latest` / `migrate:rollback`
- Any raw `psql`/`mysql` command

There is no database connection from inside the factory. Migration
verification (running the migration locally, checking idempotency,
running `db:migrate:status`) is the human reviewer's job.

This boundary is hard: even `alembic check` might connect to a
metadata database. We avoid the whole class.

### One file per WorkItem

A multi-step migration ("add column, backfill data, add NOT NULL
constraint") is **multiple WorkItems**. Each gets its own scaffold
PR; the human chains them on prod in the right order.

This forces the dangerous parts (data backfill, locking concerns) to
sit in separate review surfaces where they can be discussed, rather
than buried in a single 200-line migration.

## The spec

```json
{
  "toolchain": "alembic" | "django" | "rails" | "knex" | "raw-sql",
  "name":      "add_email_to_users",
  "app":       "users"
}
```

`toolchain` is optional. If absent, the skill runs the detector
([`scripts/skills/migration-detect.sh`](../../scripts/skills/migration-detect.sh))
and uses its first match in canonical order: alembic, django, rails,
knex, raw-sql.

`name` is required. Must match `^[a-z][a-z0-9_]{0,59}$`. Used as
part of the filename per toolchain convention.

`app` is required only for Django (the `<app>/migrations/` directory
that holds the new file).

## Per-toolchain output

| Toolchain | Path                                                | Boilerplate                                                          |
| --------- | --------------------------------------------------- | -------------------------------------------------------------------- |
| alembic   | `migrations/versions/<rev>_<name>.py`               | `revision`, `down_revision`, `upgrade()`, `downgrade()`              |
| django    | `<app>/migrations/<NNNN>_<name>.py`                 | `Migration` class, empty `dependencies` and `operations` lists       |
| rails     | `db/migrate/<YYYYMMDDHHMMSS>_<name>.rb`             | `class <CamelCase> < ActiveRecord::Migration[7.0]; def change; end`  |
| knex      | `migrations/<YYYYMMDDHHMMSS>_<name>.js`             | `exports.up`, `exports.down` (async)                                 |
| raw-sql   | `migrations/<YYYYMMDDHHMMSS>_<name>.sql`            | `-- Up`, `-- Down` sections                                          |

Sequence/timestamp specifics:

- **Alembic** uses a 12-hex revision id. Random by default; pass
  `--rev <hex>` for deterministic tests.
- **Django** scans the target `<app>/migrations/` directory, finds
  the highest leading 4-digit sequence, and uses `that+1` (zero-
  padded). An empty `migrations/` produces `0001_<name>`.
- **Rails / Knex / raw-SQL** use a UTC `YYYYMMDDHHMMSS` timestamp.
  Pass `--now <stamp>` for deterministic tests.

## What the smoke test covers

[`scripts/test/migration-smoke.sh`](../../scripts/test/migration-smoke.sh)
runs **31 fixture-based checks** without any external binaries:

- Detector identifies each of the five toolchains in a synthetic
  fixture tree.
- Detector returns nothing on an empty repo and on an "unknown" repo
  with a `migrations/` dir holding `.py` files but no `alembic.ini`.
- Detector exits 2 on a bad `--root`.
- Scaffolder produces the right filename and required boilerplate for
  each toolchain.
- Django scaffolder increments the sequence (0002 → 0003) and starts
  at 0001 in an empty migrations dir.
- Filename collision exits 2.
- Bad name (uppercase, hyphen) exits 2.
- Unknown toolchain, missing `--migration-name`, and Django without
  `--app` all exit 2.

## What this skill does NOT do

- It does not write migration bodies.
- It does not run `--autogenerate` or any database introspection.
- It does not execute migrations.
- It does not touch models / schema files.
- It does not auto-merge: every PR carries `needs-human`.
- It does not run on a schedule. Always operator-filed.
- It does not split a multi-step migration. Multi-step = multiple
  WorkItems.
